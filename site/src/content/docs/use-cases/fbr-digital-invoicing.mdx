## The problem

FBR's Digital Invoicing (DI) system takes each invoice as JSON posted to a gateway run by PRAL. The gateway rejects an invoice with an error code, such as `0104` when the sales tax on a line doesn't match the rate. Finding those problems before you post saves a round trip per mistake, and catches them in tests.

## 1. Find the rate on the invoice date

`getSalesTaxRate()` returns the standard rate in force on a date, with the law it comes from and an official document. The standard rate on goods has been 18% since 23 February 2023 (Sales Tax Act 1990, s. 3(1), as amended by the Finance (Supplementary) Act 2023; [FBR's consolidated Act, updated up to 30 June 2026](https://download1.fbr.gov.pk/Docs/20267171373418951SalesTaxAct1990updatedupto30.06.2026.pdf); checked 18 November 2026).

## 2. Check the buyer's NTN

An NTN in the invoice is 7 digits, and a CNIC 13 (PRAL's specification and error guide, checked 18 November 2026). `validateNTN()` checks the format; it does not ask FBR whether the buyer is registered.

<LangTabs module="use-fbr-digital-invoicing" ids={['buyer-ntn']} />

## 3. Work out the tax and build the invoice

`expectedSalesTax()` gives the tax FBR expects on one line: the value excluding sales tax × the rate for a percentage rate (`1000 × 18% = 180`), quantity × amount for a per-unit rate. `buildFbrInvoice()` fills in each line's tax this way, adds the defaults FBR's samples use, and returns the invoice with its column totals.

<LangTabs module="use-fbr-digital-invoicing" ids={['line-tax', 'build']} />

## 4. Validate before you post

`validateFbrInvoice()` returns every problem it finds, each with FBR's error code. Pass `today` to reject an invoice dated later (error `0043`).

## 5. Post it with your own code

Send the invoice to PRAL's `validateinvoicedata` or `postinvoicedata` endpoint with your own HTTP client and your own token. The library has no HTTP client and handles no tokens.

<Tabs syncKey="framework">
<TabItem label="NestJS">

```ts
import { BadRequestException, Injectable } from '@nestjs/common';
import {
  buildFbrInvoice,
  validateFbrInvoice,
  type FbrInvoiceInput,
} from 'pakdatakit/fbr-invoice';

@Injectable()
export class InvoiceService {
  prepare(input: FbrInvoiceInput, today: string) {
    const built = buildFbrInvoice(input);
    if (!built) throw new BadRequestException('Not an invoice');
    const { valid, errors } = validateFbrInvoice(built.invoice, { today });
    if (!valid) throw new BadRequestException(errors);
    return built.invoice; // post this with your own client and token
  }
}
```

use PakDataKit\FbrInvoice;

$built = FbrInvoice::build($request->input('invoice'));

## Pitfalls

- **Rounding your own way.** The specification allows 2 decimals and gives no rounding rule. The library rounds half up to the paisa and accepts a declared tax within one paisa of it; that is the library's choice, not FBR's.
- **Assuming every rate is a percentage.** Lines with a rate that is neither `N%` nor `Rs.N` (`Exempt`, combined rates) get 0 tax from `buildFbrInvoice()` unless you give the tax yourself.
- **Copying the field table's spelling.** Key names follow the specification's sample JSON (`invoiceType`, `buyerRegistrationType`), and `invoiceType` is `Sale Invoice`, as in the samples.
- **Expecting invoice totals in the JSON.** The specification has no invoice-level totals; the totals `buildFbrInvoice()` returns are for your own records.
- **Validating without `today`.** A future date (error `0043`) is only caught when you pass today's date.

## What this library does not do

- **It does not submit anything to FBR.** There is no HTTP client and no token handling; your code posts the invoice.
- **It does not check FBR's reference data.** Registration status, and whether a province, HS code, unit, rate, sale type or SRO is in FBR's lists or fits the others, need FBR's reference APIs. They are checked for presence only.
- **It does not check the original invoice of a debit note.**
- **It does not decide whether you must use digital invoicing**, or which rate, sale type or SRO applies to your goods. Those are questions for FBR's rules or your tax adviser.
- **It covers standard rates only** in `getSalesTaxRate()`: reduced rates, exemptions, the Third Schedule and further tax are not covered.
